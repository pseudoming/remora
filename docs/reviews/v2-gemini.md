## 一、V2 方案最惊艳的 4 个设计

1. **防退化断言：决策清单 Checksum** — 用结构化的 Key-Value 清单在压缩前后做 Assert 校验，相当于**给大模型的记忆系统引入了 TDD（测试驱动开发）**。这是保证系统长期运行不崩溃的神来之笔。

2. **状态脱节终极解法：文件哈希锚定** — 用 Git Commit 或文件 Hash 把虚无缥缈的自然语言记忆，死死钉在了物理代码库的特定状态上。这彻底斩断了 Agent "刻舟求剑"式的工作模式。

3. **退守的智慧：半自动打标** — 放弃纯靠大模型全自动切分话题，引入 `/topic new` 命令。让开发者像用 `git branch` 一样主动管理 Agent 的注意力，比让大模型耗费巨量 Token 去"猜"意图要精准且廉价一万倍。

4. **强拦截防杠精：旁路意图检测** — 面对用户的质疑，不给大模型用当前残缺上下文"圆谎"的机会，直接在输入网关层用正则或小模型硬拦截，强制注入温存储记录。

## 二、落地施工时的 4 个"深水区暗礁"

### 暗礁 1：异步压缩的"并发脏写" (Race Condition)

Context Manager 正在后台静默压缩时，用户在前台又发了一条关于同一 Topic 的极其重要的补充指令。当后台压缩完成并强行替换主干的热记忆时，用户的新输入会被永久覆盖丢失。

**解法（水位线/追加合并）**：锁定 `max_message_id` 水位线游标。后台只压缩这个 ID 之前的数据。完成后更新热记忆时必须执行 Merge 操作：`新热记忆 = [结构化摘要] + [msg_id > max_message_id 的新消息]`。绝不能做盲目的全量替换。

### 暗礁 2：哈希锚定过于"脆弱" (The Brittle Hash Problem)

用户可能只是加了一个空行、改了一个拼写错误，导致 `file_hash` 瞬间改变。如果 Orchestrator 因此认为整个 Topic 摘要"全部过期"并频繁报警，体验会很糟糕。

**解法（静默降级比对）**：当检测到 Hash 不一致时，不要直接废弃摘要。系统应在后台静默执行 `git diff`。如果 Diff 很短，将 Diff 喂给主干。只有实质性冲突时，才触发认知重构警报。

### 暗礁 3：CLI 形态与异步交互的线程冲突

Python 原生的 `input()` 是**阻塞主线程**的。如果用多线程强行 `print()`，会把用户输入了一半的字符冲刷得乱七八糟。

**解法（抛弃原生 input）**：必须使用全双工的 TUI 框架，强烈推荐基于 Rich 构建的 **`Textual`**。它可以划分"底部输入区（永不被冲刷）"、"中间对话区"和"侧边栏 Topic 状态树"。

### 暗礁 4：沙盒执行的"信息黑洞"与日志爆炸

如果子代理输出了 5 万行的 Stack Trace，不加节制地存入 SQLite，数据库会瞬间膨胀。

**解法（强制首尾截断）**：对于长日志，**只保留头部 100 行和尾部 200 行**，中间用 `...[Truncated 48000 chars]...` 替换。这是保命机制。

## 三、技术栈建议

1. **API 网关：`LiteLLM`** — 用 OpenAI 标准格式适配几乎所有模型，自带 Token & Cost 成本追踪钩子。
2. **工具标准化：MCP (Model Context Protocol)** — Agent 实现为 MCP Client，直接白嫖社区写好的 mcp-server-filesystem 和 mcp-server-sqlite。
3. **Phase 1 沙盒：避开 Docker** — 子代理直接用 `subprocess` + Git 临时分支实现无状态，比启动容器快 100 倍。
