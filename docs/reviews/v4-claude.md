## 二、三处真实遗留问题

### 问题 1：Worktree 方案的"接受变更"流程缺失（Phase 1 必须解决）

v3 的临时分支方案里有一句"如果结果被采纳，提示用户合并"——这句话在 v4 切换到 Worktree 后消失了。Worktree 创建在 `../.agent_workspace_<uuid>/`，是物理上独立的目录，子代理修改的是那个目录里的文件，用户的 `./src/` 完全没有变化。

**这是 Phase 1 的核心交互流程，不定义就没法实现。** 需要明确：子代理执行成功后，系统如何把变更交还给用户？

建议定义如下协议：

```
执行成功 → 展示 changed_files 的 diff
→ 用户确认 [y/n]
→ y: 将 worktree 中已改动的文件逐一 copy 回主工作区（不做 git merge，避免分支管理复杂性）
→ n: git worktree remove --force，丢弃
```

用文件级 copy 而非 git merge，是因为 Phase 1 的用户工作区状态不一定干净，强制 merge 容易出冲突。等 Phase 3 再考虑用 cherry-pick 做更精细的历史管理。

---

### 问题 2：`facts` 字段悬空（Phase 2 会遇到）

Topic 数据结构里出现了 `"facts": []`，文档后面说"字段严格区分 facts、decisions、constraints、open_questions"，但 `facts` 是什么、和 `key_decisions` 的边界在哪里，完全没有定义。

这不是无关紧要的细节——压缩 prompt 需要告诉 LLM 该往哪个字段里填什么，实现者遇到这个空字段会有两种结果：要么直接忽略它，要么随意填，两种都会导致数据不一致。

**建议**：要么给出定义（如"facts = 客观事实，如 API 限制、环境约束；decisions = 主动选择，如采用哪个方案"），要么删除这个字段，把内容合并进 `constraints`。留一个空字段比删除它代价更高。

---

### 问题 3：`compression_confidence` 的计算方法未定义（Phase 2 会遇到）

Topic 里有 `"compression_confidence": 0.92`，但这个数字怎么来的？

目前可能的理解：
- 让 LLM 自评（"你对这次摘要的信心有多高？"）——不可靠，LLM 倾向于给高分
- Checksum 通过 = 1.0，失败一次 = 0.7，失败两次 = 0.4——可量化，但阈值任意
- 保留的决策点数 / 原始决策点数——有实际含义，但实现复杂

不定义计算方法，这个字段就只是个装饰。Phase 2 实现压缩时必须决定它，否则会被实现者随便填 1.0，失去意义。

**建议**：Phase 2 先用最简单的定义——Checksum 比对结果的通过率（`保留的关键决策数 / 压缩前提取的关键决策数`），是可量化的整数比，不依赖 LLM 自评。

## 三、一处小建议（不阻塞开发）

**意图检测的"之前"误报**：正则里包含"之前"作为触发词，但这是一个极高频的中文词，"你之前提的那个方案挺好的"同样会命中。误报后会触发温存储检索，虽然有手动 `/recall` 兜底，但高频误报会让用户觉得工具在乱动。

建议把"之前"替换为更精确的短语组合，如"之前不是说"、"你不是说之前"，或把"之前"改为需要配合否定词才触发（"之前 + (不|错|没|但)"）。这在 Phase 2 实现意图检测时一并处理即可。
