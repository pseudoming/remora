# Review v5 (Qwen)

> 这份《长周期 Code Agent 认知架构与工程实施方案（v5）》是一份**极具深度、高度务实且逻辑自洽**的设计文档。这个设计和概念不仅真实成立，而且切中了当前 AI Coding Agent 领域最核心的痛点，其工程实施方案具备极高的落地可行性。
>
> 你没有陷入"试图训练一个拥有无限完美记忆的超大模型"的乌托邦陷阱，而是采用了**"用传统软件工程的确定性来约束和辅助概率模型"**的正确路径。

---

## 一、为什么这个设计"真实成立"？

### 1. 哲学层面的降维打击：用"工程确定性"对抗"模型概率性"

LLM 的本质是概率预测，必然会产生幻觉和遗忘。你的设计没有强求 LLM "不犯错"，而是通过 `compression_confidence`（Checksum 校验）、`Git Worktree`（物理隔离）、`强制 Recall`（硬规则拦截）等工程手段，**把 LLM 的错误限制在可控的沙箱内，并提供了低成本的"后悔药"**。这种"防御性编程"思想在 Agent 架构中极其珍贵。

### 2. "后优先原则"与"决策清单校验"是神来之笔

在长对话中，最可怕的不是遗忘，而是**"早期被否决的错误方案污染了最终认知"**。
- "后优先（Later-Wins）"强制 LLM 在压缩时进行状态覆盖。
- "提取清单 → 压缩 → 比对清单"的 **Checksum 机制**相当于给 LLM 的输出加上了单元测试，用极低的计算成本换取了记忆摘要的结构化保真度。

### 3. Git Worktree 隔离与"变更回传协议"

这是整个方案中最具工程美感的部分。
- `Git Worktree` 实现了完美的代码级隔离。
- V5 增加的**"展示 Diff → 用户确认 → 文件复制"**协议，彻底杜绝了 Agent 擅自 `git merge` 导致的冲突灾难，把"控制权"死死留在了人类手里。

## 二、落地时必定遇到的 5 个"暗坑"与优化建议

### 1. 压缩的"有损性"陷阱：丢失了 Rationale（理由）

**问题**：在 `key_decisions` 中，如果只记录"方案 A 被否决，方案 B 被采用"，几个月后，当遇到类似场景时，Agent 可能会再次提出方案 A，因为它**忘记了当初为什么否决 A**。

**建议**：在 Topic 的数据结构中，强制要求 `key_decisions` 包含 `rationale`（深层理由）字段。压缩 Prompt 必须指示："不仅要记录最终决策，必须提炼出**否决其他方案的核心约束或技术原因**"。

### 2. Git Worktree 的"环境依赖"与 Monorepo 挑战

**问题**：Worktree 隔离了**代码**，但没有隔离**运行环境**。如果子代理需要跑测试，而测试依赖本地的 `.env` 配置、未提交的本地数据库数据、或特定 Docker 容器，Worktree 里的代码可能因找不到环境依赖而运行失败。大型 Monorepo 中 `git worktree` 可能非常慢。

**建议**：子代理的 System Prompt 中包含"环境探测"工具，执行前先检查依赖。对于非 Git 项目或 Monorepo，提供基于 `rsync` 或 `Docker Volume` 的轻量级沙箱回退方案。

### 3. 意图检测的"假阳性"打断心流

**问题**：正则硬拦截可能在正常讨论中误触发——用户说"参考我们**之前**讨论的那个高并发架构"时触发强制 Recall，系统检索一堆无关历史注入上下文，反而干扰 LLM 当前推理。

**建议**：不要直接硬拦截并注入。当正则命中时，在 System Prompt 中插入高亮提示：`[System Alert: 用户提及历史记忆，建议你优先调用 recall_memory 工具确认事实，不要凭印象回答]`。让 LLM 自己决定是否调用，既保留防御性又增加灵活性。

### 4. 温存储 FTS5 的"语义盲区"

**问题**：SQLite FTS5 trigram 对精确的报错信息、函数名检索极佳。但如果用户问"我们当时讨论的那个关于优化数据库连接池的方案是什么？"，FTS5 可能因为原文中没有"连接池"这三个字（可能写的是"HikariCP 配置"）而检索失败。

**建议**：Phase 3 引入冷存储时，对 `messages` 表增加轻量级 **Embedding 向量字段**，采用**Hybrid Search（FTS5 关键词 + 向量语义）**。

### 5. 主干 Agent 的"Topic 索引爆炸"

**问题**：随着项目推进可能有 50 个 Topic。如果热记忆中注入所有活跃 Topic 摘要，依然会导致上下文超限或注意力分散（Lost in the Middle）。

**建议**：主干 Agent 的热记忆中，只保留**"Topic 索引（ID + 一句话标题 + 关联文件）"**。只有当 Planner 识别出当前任务与某个 Topic 相关时，才通过 Tool 动态拉取该 Topic 的详细摘要（Lazy Loading）。

## 三、对 V5 修正清单的点评

V5 的修正清单展现了极强的**"工程克制力"**：

1. **放弃 LLM 语义路由，改用正则+手动兜底**：极其明智。在长周期任务中，把路由决策交给概率模型是灾难，用确定性的正则和显式命令（`/recall`）兜底，能省去无数 Debug 的时间。

2. **`facts` 与 `key_decisions` 边界清晰**：区分"客观环境限制"和"主观架构选择"，对于后续代码生成和重构至关重要。

3. **动态缓冲替代"最近 3 轮"**：修复了"时间黑洞"问题。基于 Token 阈值和水位线的动态缓冲是更科学的做法。

## 最终结论

这份设计**完全成立，且具备成为行业标杆的潜力**。

它最大的价值在于提出了一句振聋发聩的口号：**"Token 是便宜的，心流是昂贵的；计算可以浪费，信任不能断裂。"**

建议**严格恪守 Phase 1 的边界**，先把"无状态执行 + 脏工作区处理 + 基础温存储"跑通。只要这个最小闭环（Sub-agent 隔离执行且不弄乱用户代码）做好了，哪怕没有 Topic 压缩，它也已经超越了市面上 80% 的套壳 Coding Agent。

祝项目顺利！这是一个非常值得做、且能真正改变开发者工作方式的硬核工程。
