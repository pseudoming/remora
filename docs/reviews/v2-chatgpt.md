# Review v2 (ChatGPT)

> 这版比上一版**更像能做出来的产品方案**了。我的结论是：**有落地价值，而且已经进入"值得做 MVP"的阶段**，但离"可稳定长期运行"还差几个关键硬点。

---

## 我的总体判断

你这次的调整是对的，尤其是这四个变化：

1. **Topic 先手动、后自动** — 先把话题边界交给用户或主干显式标记，能明显降低错误聚类带来的记忆污染。
2. **压缩前做决策清单 checksum** — 这比单纯让模型"总结得好一点"靠谱得多。你在给压缩结果加结构化验收。
3. **文件哈希锚定** — 这是把"摘要"拉回现实代码状态的好办法，能防止记忆和代码漂移。
4. **异步后台压缩** — 这让主交互不被整理工作卡住，工程上是必要的。

## 这份方案已经成立的部分

### 1) 结构方向是对的

你现在的核心不是"让模型记得更多"，而是：让记忆**可分层**、让记忆**可回查**、让记忆**可纠错**、让执行**可隔离**。这四件事都对，而且是 code agent 长周期协作里真正缺的东西。

### 2) MVP 路线合理

Phase 1 → Phase 2 → Phase 3 的拆法是合理的。尤其是先做：无状态子代理、温存储、手动 recall。这个顺序没问题。先验证协作闭环，再做自动压缩，避免一开始把系统做得太重。

---

## 现在还缺的硬问题

### 1) Topic 现在还不够"可计算"

你定义了 topic，但还没把它拆成足够稳定的数据面。现在的 `summary`、`key_decisions`、`dependencies` 这些字段是有用的，但还不够。

建议补成更明确的四块：**facts**（事实）、**decisions**（决策）、**constraints**（约束）、**open_questions**（未决问题）。这样后面压缩、检索、校验都能分别处理，不会把"事实"和"判断"混在一起。

### 2) 压缩结果需要版本号，不只是更新时间

你现在写了 `last_updated`，但不够。因为压缩不是单次动作，而是会反复修订。

建议每个 topic 加：`version`、`compressed_from_message_range`、`compression_snapshot_id`、`compression_confidence`。不然你后面很难知道：这份摘要是基于哪一批消息生成的、哪次压缩引入了偏差、当前摘要是不是过期了。

### 3) 异步压缩会带来一致性问题

这是你方案里最容易被低估的地方。问题不是"压缩慢"，而是：用户还在继续聊、topic 还在变化、后台压缩拿到的是旧快照、压缩完之后却覆盖了新的状态。

所以你必须加一个机制：**压缩必须基于只读快照，提交时做版本校验；版本不一致就丢弃或重试。** 否则异步会把系统搞乱。

### 4) checksum 只能防"漏掉"，防不了"写歪"

你现在的决策清单校验是好东西，但它只能发现：决策没保留、条目被删了。它发现不了：决策被改写成另一个意思、语义被弱化、约束被偷偷改成了"建议"。

所以 checksum 之外还要有**语义级校验**。最简单的做法就是给每个关键决策打一个固定结构：

```json
{
  "decision": "...",
  "status": "confirmed/overturned/open",
  "evidence": ["msg_12", "msg_18"]
}
```

后续压缩时，不只是比对文本是否存在，而是比对状态和证据链是否还在。

### 5) 文件哈希锚定有用，但不能只靠 hash

文件 hash 很容易在这些场景失效：重构、格式化、大范围移动、局部修改后整体 hash 变化。

所以建议升级为：`file path`、`symbol/function name`、`git commit`、`line range`、`content hash`。这样既能定位代码，也能容忍正常重构。

### 6) Recall 触发不能只靠正则

"用户质疑历史记忆"这个判断很重要，但别把它做得太硬。用户表达方式很散："不是，你前面那句不对"、"我记得你刚才说的是另一个"、"这和前面那个结论冲突"、"你是不是忘了上文"。单靠规则会漏。

建议是：正则做高精度触发、小模型/分类器做补充判断、低置信度时也先查回忆，不要硬猜。

## 我对这版的评价

这是个能做的系统，但不是"一个大功能"。它更像一个**长期协作底座**，不是一个单点能力。真正值钱的不是某个摘要功能，而是：任务分解、topic 管理、原文回查、压缩校验、代码状态锚定、子代理隔离。这些拼起来，才会让长期 code agent 不那么容易失控。

---

## 优先级建议

### 第一优先级：先把"记忆正确性"做稳

先做这三样：topic + provenance、recall_memory、版本化压缩。这三样做稳，系统就已经比大多数 agent 强很多了。

### 第二优先级：再做"执行隔离"

把子代理沙箱、白名单命令、路径限制补稳。这是 code agent 真正会出事故的地方。

### 第三优先级：最后才做"经验库 / 冷记忆"

冷记忆很有价值，但不是 MVP 核心。先别为了它把系统复杂度拉太高。

---

## 一句话结论

**这版已经从"概念正确"进化到"工程上值得试"的阶段了。** 但要真正落地，还必须补上三件事：**版本化、快照一致性、语义级校验**。这三个不补，系统会在长对话里慢慢失真；补上了，它才有机会成为真正可用的长期 code agent 底座。
