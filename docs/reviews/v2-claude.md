## 二、仍需解决的三处问题

### 问题 1：Checksum 的提取机制仍然欠具体

文档说"用简单规则/小模型提取决策清单"，但"什么算一个决策"这个问题本身就不简单。

考虑这段对话：

> 用户："就用 A 方案吧"
> Agent："好的，A 方案更合适"
> 用户："等等，其实 B 更简单，改用 B"

压缩前要提取的 checksum 应该是"采用 B 方案，A 方案被否决"——但正则和小模型都容易提取出"A 方案"和"B 方案"两个条目而不知道方向性。

**具体建议**：把 checksum 格式定义为三元组 `(主体, 状态, 触发条件)`，例如：

```json
{
  "item": "频率限制方案",
  "status": "adopted",  // adopted | rejected | pending
  "value": "动态间隔，基于403响应"
}
```

在压缩 prompt 里明确要求 LLM 输出这种格式的决策清单，再做 diff。这比"检查关键词是否存在"可靠得多。

---

### 问题 2：异步压缩的并发边界未定义

文档说"通过原子操作替换热记忆"，但没有定义这个原子边界。有一个真实的竞争场景：

1. 后台开始压缩 topic A（基于消息 1-50）
2. 用户继续对话，产生了消息 51-55，这些消息引用了 topic A 的内容
3. 压缩完成，摘要基于消息 1-50，但消息 51-55 里有对 topic A 的修正
4. 摘要被写入热记忆，主干上下文里不再有原始消息 1-50，但消息 51-55 里的修正信息 Orchestrator 可能已经"知道"也可能不知道

结果：摘要和当前对话状态不一致，而这种不一致不会触发任何告警。

**建议**：压缩开始时记录一个"水位线"（watermark），例如 `compression_based_on: msg_id_50`。压缩完成后检查从 watermark 到现在有无新消息引用了被压缩的 topic——有的话，在摘要末尾注记"注意：此摘要后有新增讨论，见消息 51-55"，而不是直接丢弃这个信息。

---

### 问题 3：子任务的 topic 相关性判断

这是方案里最大的隐性空白。文档多处提到"只包含与本次任务相关的 topic 摘要"给子代理，但没有解释如何判断"相关"。

比如 Orchestrator 分发的任务是："修复 bilibili.py 的超时错误"，系统如何知道应该注入 topic "B站爬虫频率限制" 而不是 topic "数据库连接池配置"？

目前可能的做法：

- 关键词匹配（脆弱：用户可能用不同措辞）
- LLM 判断相关性（多一次 API 调用，且判断本身可能出错）
- 完全注入所有 topic 摘要（安全但浪费 token，topic 多了上下文一样会膨胀）

**建议**：在 Topic 对象里增加一个 `associated_files` 字段（这在 v2 里其实已经有了），用**文件路径匹配**作为相关性的第一层过滤——子任务涉及哪些文件，就注入与这些文件关联的 topic。这是确定性的、零 LLM 成本的。语义相关性作为第二层可以后期加。

## 三、一个小但值得注意的新问题

**意图检测的误报率没有设计容错**

"正则/小模型检测用户是否在质疑历史"这个机制，误报代价不对称：

- 漏报（用户在质疑但没检测到）→ Agent 可能基于错误摘要继续，危害大
- 误报（用户没在质疑但触发了 recall）→ 多花 token 且打断用户流程，危害小

但如果误报率高（比如用户说"这个问题我之前也遇到过"），每次都去检索温存储，会让工具变得很烦。

**建议**：给用户一个显式的 `/recall [关键词]` 命令作为保底机制，并在 System Prompt 里告诉模型主动建议用户使用这个命令，而不是完全依赖自动检测。这样即使自动检测漏掉了，用户有明确的手段触发，也知道这个工具存在。

## 四、一处值得补充的细节：SQLite 健壮性

方案没提，但工程上必须考虑：

- 启用 WAL 模式（`PRAGMA journal_mode=WAL`），避免写入崩溃导致数据库损坏
- 压缩操作用事务包裹，中途崩溃时原始消息仍在，摘要未替换，下次启动可重新压缩
- 定期备份（哪怕只是 `cp` 一份到同目录）

这不是架构问题，但在 Phase 1 实现时就应该做，否则用户数据丢失会直接毁掉产品信任度。
