## 二、仍需解决的三处问题

### 问题 1：Git 分支隔离有两个真实的 Edge Case

Phase 1 的执行隔离方案（临时分支 + reset）是务实的选择，但有两种情况会直接导致子代理执行失败，文档没有处理：

**Case A：用户有未提交的改动（unstaged/staged changes）**

执行 `git checkout -b agent-temp-{uuid}` 时，未暂存的改动会"跟随"到临时分支，或直接报错（取决于 git 版本和冲突情况）。子代理在这个状态下做的修改，和用户的 WIP 改动混在一起，最后 reset 时可能把用户的改动一并抹掉。

**Case B：项目没有初始化 git**

这种情况比想象的更常见：一个 Python 脚本目录、一个临时实验项目。这时整个隔离机制直接无法启动。

**建议**：在 Sub-agent Factory 启动前增加一个环境探测步骤：
- 有 git 且工作区干净 → 用临时分支方案
- 有 git 但工作区有改动 → 先 `git stash`，执行完再 `git stash pop`，并告知用户
- 无 git → 退化到"文件快照备份"方案（执行前 `cp -r` 相关文件到临时目录，失败时恢复）

这个探测逻辑在 Phase 1 就需要，否则第一个不用 git 的用户会直接报错。

### 问题 2：`associated_files` 的"冷启动盲区"

文档在 3.3 里说子代理的 Topic 过滤依赖 `associated_files` 匹配文件路径。但 `associated_files` 是在**压缩时**才写入的（3.2.4）。

这意味着：在 Phase 2 早期，刚创建的 Topic 还没有被压缩过，`associated_files` 为空，文件路径过滤会返回空结果——子代理要么拿不到任何 Topic 上下文，要么（如果 fallback 是注入全部）又回到了没有过滤的状态。

文档对这个 fallback 行为没有定义，而这在 Phase 2 第一周就会遇到。

**建议**：在 Task Dispatcher 处增加一个"主动写入"动作：当 Orchestrator 分发的子任务明确涉及某个文件（例如"修改 `src/crawler/bilibili.py` 的超时逻辑"），在分发前就把这个文件路径写入当前活跃 Topic 的 `associated_files`（hash 也在此时计算）。不必等到压缩。这样 `associated_files` 在 Topic 存活期间就会持续积累，而不是只在压缩后才有数据。

### 问题 3："倒序压缩"的提示词实现需要澄清

这是一个容易被跳过的实现细节，但实际上是整个压缩质量的关键。

文档说"指示 LLM 从最新的消息向最早消息阅读"。但标准 API 调用中，消息是按时间顺序传入上下文的，LLM 不能真正"反向阅读"——它的注意力机制是从左到右的，后面的 token 能注意到前面的，反过来不行。

所以"倒序"的正确实现方式不是字面上把消息倒序排列（那会打乱对话逻辑，LLM 会混乱），而是在 prompt 里**明确声明修正优先级**，例如：

> "以下是一段对话记录（按时间正序）。在生成摘要时，**后发生的决策优先于早期决策**。若某个方案在后续被明确推翻或修正，摘要中只记录最终状态，并注明'早期方案已被推翻'。"

这和文档的意图是一致的，但实现方式不同。如果真的把消息倒序传给 LLM，会导致 LLM 误以为最新的消息是"之前"发生的，反而产生混乱。

**建议**：在文档中把"倒序"改为"后优先（later-wins）压缩策略"，并给出一段示意 prompt，避免实现者按字面意思把消息倒排。

## 三、一处小问题：checksum 失败后用户无感知

3.2.3 步骤 d 里，两次重试后仍失败的处理是"标记置信度较低，附加警告信息"——但这个警告在哪里展示？附加在摘要末尾的话，用户不主动查看是看不到的。

**建议**：压缩置信度低时，在主干的下一次响应开头插入一行提示：

> `⚠ Topic [B站爬虫频率限制] 压缩校验未通过，摘要可能不完整。建议 /recall 验证关键决策。`

这一行加在 Orchestrator 的输出前，不需要用户主动查看，也不会中断流程。
