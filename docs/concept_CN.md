# 长周期 Code Agent 认知架构——概念说明

> [English](./concept.md)

## 0. TL;DR

我们不试图创造一个"永不遗忘"的 Agent，而是构建一个**遗忘可控、错误可逆**的协作系统。

通过将软件工程中"高内聚低耦合"、"分层存储"、"防御性编程"等成熟思想应用到 LLM 的记忆管理，这套架构让 AI 编程助手从"短期记忆力超强但思维混乱的初级外包"，蜕变为一个**具备结构化长期记忆、可追溯决策过程、能承受高强度长期协作的资深搭档**。

**其核心差异不在于技术花哨，而在于对成本的清醒认知：**  
Token 是便宜的，心流是昂贵的；计算可以浪费，信任不能断裂。

---

## 1. 我们面临的问题：上下文腐烂

在与 AI Coding Agent 长期协作时——比如一个持续数天、跨越上百轮对话的项目——会出现一种被称为**"上下文腐烂"**的现象：

- 早期的关键决策、约束条件、被推翻的方案，逐渐被后续大量的日志、试错和闲聊稀释。
- Agent 的注意力在膨胀的上下文中迷失，开始忘记之前确认过的规则，重复犯过的错误，甚至推翻已经定好的架构。
- 用户被迫反复纠正、重新解释、重开会话，心流不断被打断，项目维护成本陡增。

这不是单个模型能力的问题，而是**上下文作为一种认知资源，在没有主动管理的情况下必然走向熵增**。现有解决方案要么粗暴截断历史（丢失信息），要么无差别摘要（破坏结构），都没有从根本上解决"认知衰减"的问题。

---

## 2. 核心理念：用计算换认知安全

**在长周期、高价值的 Agent 协作中，Token 是廉价的计算资源，而开发者的心流连续性和项目状态的可追溯性才是真正昂贵的资产。**

因此，我们主动支付"认知整理税"——系统会周期性、结构化地花费额外的 Token 来整理、压缩、索引对话历史，以换取长期协作中记忆的清晰、准确和可修正。这类似于软件工程中的重构：短期投入额外工作量，但避免了系统在未来因混乱而彻底崩溃。

ROI 算法很简单：多花几百万 Token 进行高质量记忆整理的成本，远低于一次上下文腐烂导致的项目返工、线上故障或开发者心流重置的代价。在严肃的代码维护场景中，这个交换无比划算。

---

## 3. 核心设计原则：高内聚低耦合的记忆管理

将传统软件工程的模块化原则应用到 Agent 的长期记忆设计：

- **高内聚**：每个话题内部包含该话题完整且自洽的决策脉络——采用了什么方案、经历了哪些推翻、为什么做出这些选择、仍有哪些约束和开放问题。
- **低耦合**：话题之间通过显式的依赖关系连接，而不是让信息隐式地散落在成百上千条消息的各个角落。

这样，对话历史就从一张混乱的"消息网"，变成了一幅结构化的"记忆地图"。每个话题都是一个可独立理解、可单独更新、可追溯来源的记忆模块。

---

## 4. 系统如何工作：三大核心机制

### 4.1 分层记忆：热、温、冷三层存储

系统将记忆分为三个层级：

- **热记忆**：直接放入大模型推理窗口的内容，包括静态全局指令、所有活跃话题的结构化摘要索引（详细摘要按需加载）、以及自上次整理以来尚未压缩的近期对话。保证当前交互的连贯和响应速度。

- **温记忆**：对话的完整原始记录，按话题和时间索引，存储在本地 SQLite 数据库。它不进入上下文，但可以随时被检索调出。当用户质疑 Agent 的记忆时，系统会强制从这里调取原文，修正当前认知。**压缩是可逆的——摘要可能有偏差，但原始事实永不丢失。**

- **冷记忆**：从历次项目中提取的通用规则、踩坑记录、模式，沉淀为长期可复用的知识，在未来的任务中自动推荐。

### 4.2 话题化压缩：后优先原则与校验

当热记忆中的未压缩消息积累到阈值，系统按话题进行压缩，将原始对话转化为结构化摘要。

这一机制的核心是**结构化决策**——将对话中的关键判断提炼成不可漂移的约束：

```json
{
  "decision": "不引入 Redis",
  "status": "confirmed",
  "rationale": "项目规模小，引入 Redis 增加运维复杂度，本地内存缓存足够",
  "negated": "任何外部缓存层，包括「只用于这一个功能」的场景",
  "user_confirmed": true,
  "evidence_msg_ids": [52]
}
```

关键设计：
- **强制记录 `rationale`**：不仅记录"做了什么"，也记录"为什么"，以及明确记录"决定不做什么"及其原因。
- **用户硬锚点**：`user_confirmed: true` 的决策进入不可绕过的压缩校验清单，不能被静默丢弃。

压缩过程遵循四项原则：

1. **边界识别**：话题划分通过显式命令手动管理，不依赖 LLM 自动猜测——这是设计选择，不是妥协。系统在检测到话题偏离时会建议新建话题，但决定权始终在用户手中。

2. **后优先压缩**：生成摘要时，明确指示"后来的决策覆盖早期的"。如果某个方案在后续被明确推翻，摘要中只会保留最终状态，并注明推翻记录及深层原因。

3. **决策清单校验**：压缩前先提取一份结构化决策清单，压缩后对比清单上的关键决策是否完整保留。如果通过率不达标，摘要会被标记为"低置信度"并提示用户复核。这种校验机制为 LLM 的概率性输出提供了确定性兜底。

4. **异步执行**：压缩在后台线程进行，不阻塞用户的正常交互。

### 4.3 无状态执行：用完即焚的子代理

当需要执行具体的代码操作时，主干 Agent 不会亲自下场，而是派发任务给一个**临时的、环境隔离的子代理**：

- **隔离沙箱**：子代理在一个独立的 Git Worktree 中运行，完全不触碰用户正在编辑的代码。任务完成后，展示变更差异给用户确认，由用户决定是否应用。
- **用完即焚**：子代理完成任务后立即销毁，不留下任何状态，从根本上杜绝了执行过程对主干认知的渐进污染。
- **完整追溯**：子代理报告所有修改过和读取过的文件，确保代码之间的隐式依赖不被遗漏。

---

## 5. 防守型设计：承认不完美，但可修正

这套架构的核心哲学是**防御性设计**：它承认 LLM 的摘要和记忆一定会出错，因此构建了多重纠错机制，而不是追求不切实际的"完美记忆"。

- **温存储原文**：任何被压缩的信息，都可以通过关键词检索出当时的完整对话。
- **主动召回**：当系统检测到用户输入可能涉及对历史的质疑时，会在 System Prompt 中提示 LLM 优先使用召回工具确认事实，而不是仅依赖摘要。
- **用户手动召回**：提供显式的 `/recall` 命令，用户可以随时主动翻阅任何历史片段。

这使得系统就像一个资深的工程师：它会做笔记、会总结，但也知道笔记可能记错，所以始终保留着原始记录，并在需要时立即去翻查。
